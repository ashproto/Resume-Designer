# On Paper iOS editor and iPhone Duo design research

Research date: 2026-11-05 Pacific (2026-11-06 UTC). Sources are current Apple HIG and Apple Developer documentation, read directly. Apple’s Markdown documentation was used where the web reader could not render JavaScript pages. This is design research, not a claim of physical-device validation. No product source files were changed.

## Research conclusion

The screenshots suggest two distinct problems: an editor that exposes secondary configuration before the content people want to edit, and a custom canvas/control composition that does not fully participate in Duo’s native layout. The proposed solution below is our design inference; Apple does not prescribe a particular resume editor.

Use a compact, scannable section navigator and a focused content editor. On wider layouts, present the navigator beside the detail using an adaptive system split view. Put standard app commands into real toolbar items and keep custom foreground controls inside the available safe area. Preserve document, selection, draft and scroll state as the phone opens, closes or folds.

## Fifteen core sources and their implications

1. **[Designing for iPhone Duo — HIG](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo).** Apple recommends compact and regular size-class layouts, consistent functionality/state across poses, asymmetric safe-area handling, and minimal rearrangement as the device folds. Standard system controls move vertically along the outer edge in relevant poses. Reserved regions include outer camera, active inner camera, and the fold. **On Paper inference:** keep the same editing hierarchy on both displays; expand section navigation and editing into adjacent panes when space allows. Do not implement a different UI for each named pose or detect Duo by model name.

2. **[Preparing your app for iPhone Duo — Technology Overview](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo).** Apple specifies navigation-container bar support rather than standalone/custom bars. Toolbar items with both icon and title adapt to vertical, horizontal and overflow presentations. By default, a custom-view toolbar item or title-only item stays horizontal; custom views need explicit axis support to participate vertically. Inspectors retain horizontal bars; multi-column split views have context-dependent bar placement. **Inference:** decompose the current floating palette into standard toolbar actions. Keep a wide zoom control as a deliberate accessory instead of expecting its custom pill to turn into a vertical item. Keep all actions accessible through overflow.

3. **[Layout — HIG](https://developer.apple.com/design/human-interface-guidelines/layout).** Layouts should adapt to size class, window size, orientation, locale, Dynamic Type and hardware occlusion. Safe areas protect foreground content from bars and camera hardware; layout guides support readable widths. **Inference:** derive document fit and panel width from the actual containing view, including each edge’s inset independently; avoid global screen dimensions and fixed device sizes. Backgrounds may bleed outside safe areas while editable text and controls stay clear.

4. **[Lists and tables — HIG](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables).** Lists support hierarchy, editing, addition, deletion and reordering. Apple specifically recommends succinct rows and navigating to detail when long content would create oversized rows. Appropriate row selection feedback communicates location. **Inference:** section rows show a clear title and brief preview/count. Selecting Summary opens its content editor rather than expanding a screen-height collection of configuration controls. Selected section remains visibly highlighted in a wide layout.

5. **[Disclosure controls — HIG](https://developer.apple.com/design/human-interface-guidelines/disclosure-controls).** Frequently used controls belong high in the disclosure hierarchy; advanced controls can remain hidden until relevant. Disclosure labels should explain what appears. **Inference:** keep content editing primary and expose a clearly named Section options destination or menu for Area, Parent group, Typography and Delete. Preserve group expansion in the navigator. A disclosure is not a reason to place every field in every expanded card.

6. **[Split views — HIG](https://developer.apple.com/design/human-interface-guidelines/split-views).** Split views express relationships between primary and secondary content. They should remain navigable as available width changes, and hidden panes must be recoverable. **Inference:** use section list → selected-section detail as the relation; make narrow presentation a standard stack and wide presentation a split view. Avoid using an arbitrarily huge single form on the inner display.

7. **[Sheets — HIG](https://developer.apple.com/design/human-interface-guidelines/sheets).** Apple recommends considering alternatives for prolonged/complex editing, avoiding stacked sheets, and preserving clear Back, Close and Done semantics. Full-height content creation can be preferable to a medium sheet. **Inference:** treat resume editing as an enduring navigation destination or a full-height editing surface, with detail navigation within it. Reserve sheets for bounded tasks such as section appearance. Do not use Done to imply an explicit save if the existing document model autosaves; show the real behavior accurately.

8. **[Text views — HIG](https://developer.apple.com/design/human-interface-guidelines/text-views).** Long or formatted editable text belongs in a text view. It should stay legible with Dynamic Type, support useful selection/copying, and use an appropriate keyboard. **Inference:** Summary needs a focused, comfortable multiline editor with keyboard-aware layout. In list previews, render supported formatting readably rather than exposing Markdown delimiters. Preserve canonical text/formatting; a visual polish must not silently strip stored Markdown or replace it with a lossy representation.

9. **[Toolbars — HIG](https://developer.apple.com/design/human-interface-guidelines/toolbars).** Deliberately prioritize actions, use recognizable system symbols, group related commands, limit clutter, and use standard components/backgrounds. Important navigation and critical completion actions need distinct familiar placement; lower-priority commands may move into More/overflow. **Inference:** Edit Resume, Assistant and Share should be recognizable labeled native actions; Undo/Redo remain a coherent group. Avoid a large undifferentiated capsule containing every command. Preserve group order across horizontal/vertical layouts and give icon controls clear accessibility names.

10. **[Materials — HIG](https://developer.apple.com/design/human-interface-guidelines/materials).** Liquid Glass separates functional controls/navigation from the content layer. Apple says to use it sparingly and not as the general content-card material. The regular variant supports text-heavy or potentially busy backgrounds; clear glass suits visually rich media. Standard components adapt to accessibility preferences. **Inference:** use native glass for navigation/toolbars, semantic grouped surfaces for forms, and a quiet document background. Adding more blurred cards would amplify the screenshot’s hierarchy problem.

11. **[Typography — HIG](https://developer.apple.com/design/human-interface-guidelines/typography).** Built-in text styles support hierarchy and Dynamic Type. Text should remain readable at different sizes, and layout must adapt rather than clip, truncate important content, or shrink to defeat accessibility. Minimize typefaces and preserve relative hierarchy. **Inference:** use native headline/body/subheadline styles for editor UI; keep resume output typography controls separate. Avoid duplicate section headings and tiny persistent field labels, and let controls stack at accessibility sizes.

12. **[Accessibility — HIG](https://developer.apple.com/design/human-interface-guidelines/accessibility).** Apple recommends support for larger text (ideally at least 200%), semantic adaptive colors, adequate contrast, control spacing, VoiceOver and alternatives to gestures. Its current iOS table lists 44×44 pt as the default control size and 28×28 pt as the minimum. **Inference:** choose at least 44 pt tap surfaces for this dense editor, without claiming 44 is Apple’s absolute minimum. Include labeled Move up/Move down alternatives to dragging. Verify light/dark, Increase Contrast, Reduce Transparency, Bold Text and large Dynamic Type.

13. **[ReservedRegion — SwiftUI](https://developer.apple.com/documentation/swiftui/reservedregion).** Available iOS 27.1+. Regions distinguish occlusions and divisions, expose frame/margins/state, and may be inactive. Standard split views and sheets already adapt. **Inference:** adopt this only where a custom canvas/control arrangement genuinely needs internal fold/camera geometry; ordinary edge safe areas do not encode an interior fold. Keep the baseline path working on older supported iOS versions.

14. **[toolbarVerticalEdge — SwiftUI](https://developer.apple.com/documentation/swiftui/environmentvalues/toolbarverticaledge).** Available iOS 27.1+. The read-only optional edge reflects the system’s preferred vertical-bar position in context, even if the bar is not visible; it is nil where vertical bars are never used. **Inference:** if a custom accessory needs alignment with system controls, use this environment value instead of assuming the rail is always on the right or simply mirroring it for RTL.

15. **[SwiftUI updates — September 2026](https://developer.apple.com/documentation/updates/swiftui).** Apple records arrangement views and vertical-control APIs, including control-axis preference and overflow prioritization. **Inference:** use the modern APIs selectively to refine native behavior; they are not prerequisites for simplifying the editor. See exact metadata-verified availability below.

## Exact API availability and compatibility

Runtime follow-up: [presentationSizing(_:)](https://developer.apple.com/documentation/swiftui/view/presentationsizing(_:)) explains that an explicit sizing on a root `NavigationSplitView` proposes the detail width while the sidebar keeps its own column sizing. [Page sizing](https://developer.apple.com/documentation/swiftui/presentationsizing/page) is intended for informational or compositional content. The default form sheet measured only 580pt on the test iPad and collapsed the editor; the implementation now requests `.page` for the writing surface. Installed SDK declarations confirm this API is available from iOS 18, so it does not require the newer Duo-only SDK symbols. Actual iPad testing then measured a 1210×802pt editor with a 300pt outline and editable detail, retaining selection and typed text through rotation.

**Implementation constraint:** `if #available(iOS 27.1, *)` protects runtime use but does not make symbols from an unknown SDK compile in Xcode 26.6. Prefer existing standard navigation, toolbar and safe-area APIs for the baseline; using new symbols requires both appropriate SDK/compiler compilation guards and runtime availability, or a deliberate CI toolchain update. Do not invent hinge APIs or new layout constants.

## Proposed On Paper design, distinguished from Apple guidance

- Compact: an editor-level navigator for Header, Main content and Sidebar; succinct section rows with readable previews/counts. Selecting a section opens a focused content editor, with an accessible options menu and a clear path back.
- Wide: the same navigator and selected editor coexist. Preserve selected section, any draft, group expansion and keyboard focus during resizing; don’t create separate content models for the two displays.
- Secondary settings: separate structure and appearance controls from text. Area/Parent/Move/Delete live in section options. Typography keeps independent title/content settings and the existing non-inheriting parent/child behavior. Reordering has both native drag/edit mode and menu alternatives.
- Canvas: fit the document to usable pane bounds, avoid right/left status rails, and make manual zoom/pan and a clear Fit action available. Recompute automatic fit on container changes; preserve manual zoom intentionally. Use system adaptive containers first, reserved regions for custom interior-fold behavior if necessary.
- Toolbar: native labeled actions with system symbols, coherent groups and platform overflow. A custom zoom display can remain horizontal where needed, but it must reserve content space and not overlap text or the rail.
- Visual style: semantic grouped backgrounds, restrained separators, one clear header per section, system type hierarchy, consistent field spacing. Glass belongs to functional chrome rather than every content card.

## Validation matrix

Test compact and regular widths, narrow and wide windows, outer display portrait/landscape, inner display portrait/landscape, fully open and partially folded, and Split View on both sides. Verify all foreground actions remain reachable around asymmetric safe areas and active reserved regions. Re-test with the keyboard, long section/document names, empty states, large Dynamic Type, RTL, VoiceOver, Increase Contrast and Reduce Transparency. Confirm native Review/Apply, Undo, grouping, typography drafts and canonical resume content paths retain their existing behavior. Simulator evidence should be reported separately from physical-device and live-provider validation.
